> 复盘日期：2026-11-05 ｜ 版本基线：V0.7.63 ｜ 立场：以"能不能持续稳定出片"为唯一标准，不以功能多少论成败

## 0. 结论先行

| 判断 | 内容 |
|---|---|
| **项目定性** | 不是一个"AI 生成工具"，而是一条**可重复、可审计、可回滚的短剧生产流水线**。工程完成度显著高于同类个人项目，生成质量受硬件天花板压制。 |
| **最强的地方** | 创作与执行之间那条**文件契约**。它让"换一套 Skill 模板，引擎一行不改"成为事实，而不是宣传语。 |
| **最弱的地方** | **没有对白配音环节**。短剧是台词驱动的，H3 出的是伴随音轨，不是可指定的台词配音。这一条不解决，"短剧"这个品类不成立。 |
| **与前沿的差距主因** | **生成能力（硬件约束）> 调度能力 > 成本控制**。成本控制结构不差，但默认参数曾低报 4 倍（已改为报实测）。 |
| **综合评分** | **6.2 / 10**（前沿=10）。工程 8.0，产品完整度 5.5，生成质量 4.5，可运维性 7.5。 |
| **一句话建议** | 别再优化"自己跑模型"的效率，把生成能力外包给 API/云，自己守**编排 + 门禁 + 成本核算**。这三件才是别人抄不走的部分。 |

## 1. 评估口径（先说清怎么判的）

不做问卷式打分。四条硬口径：

1. **能不能跑通**：以真实产物为准（`final.mp4`、`EpisodeNN.mp4` 的 ffprobe 结果），不看代码里有没有这个函数。
2. **错了会不会说**：故意制造故障（缺模型、缺集、计费未确认、竖屏出横屏），看系统是静默降级还是明确阻断。
3. **能不能只重跑一步**：改一条提示词，是否需要从头再跑一遍。
4. **钱和时间花在哪**：以 `ledger/runs` 与实测耗时为准，不看预估表。

按这四条，本项目在 (1)(2)(3) 上表现良好，在 (4) 上有明确但可控的短板。

## 3. 优势（每条都有证据）

### 3.1 契约分层：换 Skill 不动引擎

**证据**：`md2pack.py` 只做 md → JSON 的机械搬运；`pack_import.py` 只认 `pack/*.json`；引擎侧 `shots.json` 只认代号。
**实测**：用宅斗与甜宠两套完全不同的模板，各生成 4 段产物，都能导入并跑到出片，引擎侧**零改动**。
**为什么值钱**：这决定了"新增一个题材"的成本是**写一份 md 模板**，不是改代码。

### 3.2 错误会说人话，且会说对

**证据**：缺一个 LoRA 曾被告知"画图工具连不上"（人于是去重启服务，白折腾）。现已按「缺件 / 连不上」分流，并有双向断言。
**价值**：流水线越长，"错误归因错误"的代价越大——上游一个误判会让人在错误的方向上花半天。

### 3.3 门禁拦在花钱之前

**证据**：`gen_preflight` 在提交前核 守卫 → 在线 → 版本 → 节点 → 模型 → 必需输入；计费命令无 `confirm` 返回 **428**；`--engine cloud` 解析出 loopback 直接退出。
**价值**：AI 生产最贵的不是单次调用，是"跑到一半发现模型不对"。

### 3.4 任何一步能单独重跑

**证据**：`--only P01`、`--only shot_002`、`--force`、`assets --kind char`、`media.render --only ep01`。
**配套修过的一个坑**：产物清单原先整份覆盖，`--only D01` 会把 24 条台账打成 1 条。现按 `(kind,key,variant)` 合并——**清单是累计事实，不是本次运行日志**。

### 3.5 成本口径：结构是对的，但默认参数对不上真实档位

> **复盘后修正（2026-11-05 20:10）**：本节初稿依据 `cost_model.py` 的模块文档，直接采纳了
> 「消费级 27 币/任务 + 1 币/秒」。随后核对真实台账时发现两件事：
> ① `iter_ledger_records` 读的路径（`<ws>/ledger/runs`）与引擎写台账的路径
> （`<ws>/video-pipeline/ledger/runs`）不一致 —— **自校准在真实项目里从未生效过**；
> ② 修好路径后，307 条真实记录给出中位数 **45 币/段、6.07 币/秒（7s 段 138–146 币）**，
> 比内置参数高约 **4 倍**。所以「实测拟合」对模型**结构**成立，对**默认值**不成立。

**结构上是对的**：两段式（固定 + 每秒）与 GPU 运行秒式双口径，本质上按 GPU 运行时间计费 ——
四组实测的「币/运行秒」= 0.205 / 0.201 / 0.207 / 0.200，高度一致，说明模型抓住了真实计费变量。
**衍生结论站得住**：**段越碎越贵**（固定部分被摊薄得少）。

**默认值的问题**：`27 + 1×秒` 只在 2026-10-19 的某一档位上成立。真实项目档位不同（或平台调价），
于是任何基于默认值的金额都会**低报约 4 倍** —— 这比"没有预估"更危险，因为它给出了可以据此做预算的错觉。

**已改**：面向用户的金额展示不再用预估，改为直接报台账实测（`cost_model.observed()`）；
预估只保留在预算闸门里。界面价签从「27 币/任务 + 1 币/秒」改成「按平台 usage 结算」。

**价值**：可观测性仍是本项目**优于市面普遍水平**的地方——能按镜、按段、按批次回溯；
问题出在默认值，不在能不能看见。

### 3.6 交付规格有唯一真源

**证据**：`delivery_spec.py` 定 1080×1920 / SAR 1:1 / 显示比例 0.5625；归一化一律 **crop-to-fill**，绝不 pad。
**踩过的坑**：用 `SAR 59:60` 凑容器是错的——本地 `cropdetect` 查不出，平台按 DAR 必补边。这条经验是花钱换来的。

### 3.7 可审计性（这一点与项目定位高度契合）

每一步的输入、产物、耗时、花费、判定都有落点：`ledger/runs`、`_done/*.json`、`timing.py`、`usage.cost`。
**它天生像一份工作底稿**：谁做的、依据什么、结论怎么来的、能不能回溯。这在"要交付给客户"的场景里是硬通货。

## 4. 劣势（按严重度排序，不粉饰）

### 4.1 【P0】没有对白配音环节 —— 短剧的核心缺一块

**事实**：全仓 grep 不到 TTS 管线。H3 工作流带 `VAEDecodeAudio`，产出 aac 音轨，但那是**模型伴随音**，不能指定"这一句必须由这个角色用这个语气说出来"。
**后果**：观众听到的人声与剧本台词不对应，或干脆没有对白。对"海外竖屏短剧"这个品类，这等于产品不成立。
**为什么容易被忽略**：出片有音轨、ffprobe 显示 `aac 立体声`，看着是"有声音的"。
**判断**：这不是技术差距，是**流程缺口**。补一条 TTS + 口型对齐，价值大于把分辨率从 672 提到 1080。

### 4.2 【P0】8G 显存决定了成片质感天花板

**事实**：本地跑的是 `minimax_h3_fl2v_turbo_4step` + `qwen3vl_32b_int4` + int8 视频 VAE（蒸馏 + 量化）。输出 672×1216，替代工作流只有 **1 个参考图槽**。
**后果**：多角色同框时，第二个角色只能靠文本描述，一致性断崖式下降（实测 shot_001 的两张参考图被丢弃一张，日志有明说）。
**这不是选型错误**：H3 本身是 2026 年主流模型（官方 2K / 5–15s / 带音频）。问题是**消费级硬件跑不动完整权重**。

### 4.3 【P1】单机串行，没有并发

**事实**：`comfy_batch_video` 逐镜串行提交；云端 `Lease` 一次一个实例；无队列、无 worker 池、无失败自动重试编排。
**后果**：30 集 × 50 分钟 ≈ **25 小时/季**。这决定了它只能"过夜跑"，不能"多项目并行"。
**可接受的部分**：短剧是批处理场景，串行本身不是错；错在**没有进度可中断恢复的并行能力**（现在能 `--only` 续跑，但要人盯着分段）。

### 4.4 【P1】模板节奏与交付档位打架

**事实**：宅斗模板产出 10 镜 × 9–10s ≈ **92s**，而项目默认档是 **60–80s**。
**后果**：超长集要么被平台截，要么人工删镜（删镜就破一致性）。
**根因**：镜数与时长约束没有写进企划阶段，只在出片时才暴露。

### 4.5 【P1】关键配置仍在命令行

**事实**：通道确认（G0）刻意没有 UI 表单，必须 `drama models set video=cloud_comfyui --comfy-url ...`；`pack.preset` 同理。
**理由正当**（避免绕过执行依据校验），但**代价是新手第一步就卡住**。这是"安全"换"可用"的自觉取舍，不算 bug，但要记在账上。

### 4.6 【P2】文档量偏大，存在双真源漂移风险

**事实**：145 份 md / 3.07 万行。已经出现过：README 从仓库根抄相对路径到工作区后参考系失效；`workflow.py status` 被删但 `adapters` 还在调它，导致三块 UI 静默失效两个月。
**规律**：**文档不可达 = 规范不会被遵守**；**接口无测试 = 会静默腐烂**。
**现状**：后者已用"接回真源 + 测试钉住"修好，前者靠绝对路径 + 参考系声明缓解。

### 4.7 【P2】续写依赖模型自律

**事实**：`append=True` + `prior` 注入解决了"覆盖"，但"从第几镜开始 / 不要重复"仍靠提示词约束模型。
**实测**：两批连写 10 镜无重复、10/10 有 A/B 段。**但这是单次样本**。模型换版本或上下文变长时，复发概率不低。
**缺的**：机械校验（写完后比对镜号连续性，重复就报警）。这个成本很低，应该做。

## 5. 与市面前沿的差距评估

### 5.1 三个维度的评分

| 维度 | 评分 | 判断依据 |
|---|---|---|
| **生成能力** | **5.0 / 10** | 模型选型对（H3 是 2026 主流），落地被显存压到 int4 + 4step；四项硬指标落后 |
| **调度能力** | **5.5 / 10** | 有任务级 lease、断点续跑、缺口退出码；无并发、无队列、无自动重试编排 |
| **成本控制** | **7.5 / 10** | 双口径模型 + 台账可回溯 + 计费前置确认；扣分项：默认参数低报 4 倍，已改为报实测 |
| 综合 | **6.2 / 10** | 工程 8.0，产品完整度 5.5，生成质量 4.5，可运维性 7.5 |

### 5.2 生成能力：差距最大，且**主要不是工程问题**

2026-11 市面前沿（公开资料口径）：

| 模型 | 单段时长 | 最高分辨率 | 原生音频 | 多参考 |
|---|---|---|---|---|
| Seedance 2.5 | 4–30s | 4K | ✅ | 最多 50 个多模态参考 |
| Kling 3.0 | 3–15s（部分模式 2 分钟） | 4K 档 | ✅ 含中文对白 | 强，跨镜头人物一致 |
| Sora 2 | 4–12s | 720p–1792×1024 | ✅ 同步音频 | 中 |
| Veo 3.1 | 4–8s | 4K | ✅ 音视频同出 | 中 |
| Wan 3.0 | 2–30s | 1080p | ✅ | 中 |
| **本项目（本地 H3 turbo 4step）** | **4–15s** | **672×1216** | **伴随音（不可指定台词）** | **1 槽（替代工作流）** |

**差距拆解**：

| 差距项 | 倍数/程度 | 性质 |
|---|---|---|
| 分辨率 | 672×1216 vs 1080p/4K ≈ **1/2.4 ~ 1/6 像素** | 硬件（8G 显存） |
| 单段时长 | 15s vs 30s–2min ≈ **1/2 ~ 1/8** | 模型 + 显存 |
| 原生对白 | 无 vs 有（Kling 3.0 / Vidu 支持中文口型） | **产品缺口，不是能力差距** |
| 参考槽 | 1 vs 最多 50 | 工作流（可换，但要显存） |
| 抽卡成本 | 本地 ￥0，但 40 倍实时 | 时间换钱 |

**关键判断**：这五项里，**只有"原生对白"是必须马上补的**（可以外挂 TTS + 口型对齐解决，不必换模型）。其余四项是"要不要花硬件钱"的商业决策，不是技术债。

### 5.3 调度能力：差距中等，且**对本场景影响被高估**

市面前沿是托管式编排：fal / Replicate / RunningHub / Comfy Deploy 都能做到提交即返回、webhook 回调、自动扩缩、失败重试。

本项目的调度特点：

| 能力 | 本项目 | 前沿 | 对本场景的影响 |
|---|---|---|---|
| 并发 | ❌ 单机串行 | ✅ 多实例并发 | **大**（30 集 25 小时） |
| 断点续跑 | ✅ `--only` / 退出码 3 | ✅ | 平 |
| 任务级资源生命周期 | ✅ `Lease` auto/keep/off | ✅ | 平（多数自建方案没有） |
| 失败处理 | ✅ 失败必停 + 停机 | ✅ 自动重试 | 中（人得看着） |
| 队列/优先级 | ❌ | ✅ | 小（项目制，不是 SaaS） |

**判断**：调度是**可以靠"多开几个进程 + 分段认领"解决 80% 的问题**，不需要重写成分布式系统。真正的差距在"没人愿意写那个分段认领的调度器"。

### 5.4 成本控制：差距最小，甚至有领先项

| 能力 | 本项目 | 市面普遍水平 |
|---|---|---|
| 单位成本建模 | ⚠ 双模型结构对，**默认值低报 4 倍**；已改为报台账实测 | 多数只看月度账单 |
| 段粒度优化 | ✅ 已知"段越碎越贵"（固定部分摊薄） | 少数团队知道 |
| 计费前置确认 | ✅ 428 + confirm | 少见（多数直接扣） |
| 免费优先 | ✅ 本地 ￥0 优先，付费需显式切换 | 少见 |
| 闲置回收 | ✅ `reap` 兜底 15 分钟 | 托管平台自带 |
| **质量-成本联合调度** | ❌ 全部镜头同一档 | 前沿已按镜头难度分档 |

**判断**：这一项**已经不是短板**。唯一值得补的是最后一行——"关键镜头用贵模型，过场用便宜模型"，这在 30 集规模下能省 30–40%。

### 5.5 差距归因（一句话）

> **差在"模型能不能跑得动"，不差在"流程管不管得住"。**
> 换句话说：这条流水线的**瓶颈在 GPU，不在架构**。把架构换成前沿模型，它能立刻上一个台阶；把模型换成前沿，架构不用动。

## 7. 演进建议（按性价比排序，不按功能诱惑排序）

### 第一档：不做就发不了片（本周）

| 动作 | 为什么排第一 |
|---|---|
| **加 TTS 配音 + 口型对齐** | 这是"短剧"的定义性能力。没有它，其余全部白干 |
| **镜号连续性机械校验** | 半天工作量，把续写从"靠模型"变成"靠检查" |
| **企划阶段约束镜数×时长** | 把 92s 问题挡在花钱之前 |

### 第二档：决定产能（本月）

| 动作 | 说明 |
|---|---|
| **分段并发调度** | 不必分布式：按镜号分段，多进程认领 + 落 `claim.json` 防重 |
| **质量分档** | 关键镜头走云端高配，过场走本地；`cost_model` 已有口径，只差一个 `shot_priority` 字段 |
| **补 8step LoRA** | 一条文件，换回 canvas 的 6 参考槽——投入产出比最高的一次硬件投资 |

### 第三档：决定能不能卖（本季）

| 动作 | 说明 |
|---|---|
| **生成能力外包** | 把"跑模型"降级为可插拔后端（本地 / 云 ComfyUI / 官方 API），编排与门禁留在自己手里 |
| **可审计交付包** | 把 `ledger` + `_done` + 合规报告打成客户可查的底稿。这是与审计背景最契合的差异化 |

## 8. 最后一段实话

这个项目的价值不在"能生成短剧"——2026 年任何一个人用可灵都能生成。

它的价值在于：**当你要交付 30 集而不是 1 条 demo 时，你需要的不是更好的模型，是一套不会静默出错的流程。**

而这套流程里最贵的部分，恰恰是那些踩过坑修出来的东西：`nodeInfoList` 是覆盖表（漏槽会串景 + OOM）、`SAR 59:60` 是错的（平台必补边）、`--only` 会把台账打成 1 条、缺一个 LoRA 会被说成"连不上"、竖屏项目出横屏。

**这些不是代码，是别人花钱买不到的判断。** 保持这个方向，比追分辨率有用得多。
