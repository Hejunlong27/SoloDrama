## 二、三个坑（都记下来）

### 坑 1 · RH 放大工作流不可用（跑了 11 分钟才报错）

预配置给的放大工作流 `2110614419863592961`（RH_Astra + Iris[iris-3]）：
上传 → QUEUED → RUNNING → **FAILED（errorCode 805 工作流运行失败，`current_outputs` 为空）**。

- 上传成功、任务被接受、跑了 11 分钟才失败
- 8 段 × 11 分钟 = 一个半小时，且没有任何产出
- 判断：这条通道在云端不可靠（至少 iris-3 那档）

**改用引擎自带的 Topaz 本地超分**，一次成功，且有自检断言。

### 坑 2 · Topaz 的模型双目录

`upscale.py` 报「模型 iris-3 的权重（*.tz3）不在 C:\ProgramData\...\models 里」。

- 本机权重实际在 **D:\ProgramData\Topaz Labs LLC\Topaz Video\models**（664 个 .tz3）
- 自动探测把 `TVAI_MODEL_DATA_DIR` 指到了 C 盘（那里只有模型定义 json，没有权重）
- 而且 **iris-3 根本没下载过权重**，只有 iris-v2

修法：写 `<项目>/video-pipeline/config.upscale.json` 指死权重目录，并改用 **iris-2**：

```json
{
  "version": 1,
  "tool": {
    "install_dir": "D:\\Program Files\\Topaz Labs LLC\\Topaz Video",
    "model_dir": "C:\\ProgramData\\Topaz Labs LLC\\Topaz Video\\models",
    "model_data_dir": "D:\\ProgramData\\Topaz Labs LLC\\Topaz Video\\models"
  }
}
```

放大自检（`upscale.py` 自带，全过）：
分辨率精确 / 宽高偶数 / 帧数一致（1604↔1604）/ 时长一致 / 音轨保留 /
无黑帧 / **确实比纯插值更锐（高频 ×1.238，拉普拉斯方差 ×3.060）**。

### 坑 3 · 烧字幕必须两遍法，且 SRT 的 force_style 不可靠

- **Topaz 的 ffmpeg 不含 libass**（无 `subtitles` 滤镜），不能在同一遍里放大+烧字幕
- 第一版用 `subtitles=ep01.srt:force_style='...Alignment=2,MarginV=280...'`
  → **字幕跑到画面顶部并被裁切**（force_style 没按预期生效）
- 改用**手写 ASS**（PlayResX/Y = 1080×1920，`Style: Default,Arial,46,...,Alignment=2,MarginL/R=80,MarginV=230`）后一次正确

烧字幕命令（cwd 必须切到 ass 所在目录，只传文件名——绝对路径里的冒号会被 libass 当成参数分隔符）：

```bash
cd <项目>/_preview
ffmpeg -y -i ep01_hd.mp4 -vf "subtitles=ep01.ass" \
  -c:v h264_nvenc -preset p5 -cq 20 -c:a copy ep01_subbed.mp4
```

## 三、字幕时间轴：没有 ASR 时的替代方案

引擎字幕管线（`stages/subtitle/scripts/subtitle.py`）依赖 `whisper-cli` 与 `ctc-forced-aligner`，
**本机两个都没装**，`--stage align` 走不通。

替代：**用剧本台词 + 段时长按句长加权**。

```python
# 每段：从 h3_prompts 的 [DIALOGUE] 取 <d>[WHO] text</d>
# 段内按各句词数加权分配该段 duration
weights = [max(len(txt.split()), 3) for _, txt in lines]
span = duration * w / sum(weights)
```

- 优点：零依赖、时间轴与画面对齐到段级（误差 < 1 句）
- 缺点：**句子内部的时间点靠猜**，若模型念白速度与台词长度差异大，会有半秒级漂移
- 这条只在「没有 ASR」时用；正式交付应装 whisper + aligner 重做

## 四、发现一个内容级问题：画面里有两个女主

`shot_001` 成片里，画面同时出现**两个 Eleanor**（左边矮的、中间高的）+ 一个 KANE。

**根因推断（待验证）**：角色卡是「16:9 纯白 + 左脸特写 + 右三视图」——
**一张卡里有同一个人的 4 个视角**。H3 多参把整张卡当参考图输入，
很可能把「4 个视角」读成了「4 个人」，于是复制出第二个女主。

佐证：本地 H3 用同一张卡、同一提示词时**没有**出现双人（本地走的是同一套多参）；
差异在云端工作流的 `ref_image_size=match` 与 6 槽位机制。

**修法方向（按代价排序）**：
1. **裁单人图作参考**：从角色卡里裁出「正面半身」一块（约 1/4 画面），作为 char_ref 传入 —— 不用重出资产
2. 角色卡改成「单人正面 + 单人侧面」两图分包，不再用三视图合版
3. 提示词里显式写 `exactly two people in frame: one woman, one man` —— 只是补丁，压不住输入端的歧义

**建议先做 1**（零成本、可立即验证）：裁一张 `char_elle_solo.png` 重跑 `shot_001`，
若双人消失即坐实根因。
