## P1 · `ingest_check.py`：两处把合法输入误判为错误

### P1-a 参考图 key 被当成路径（整集 18 条误杀）

**现象**

```
[FAIL] ep06_001: 参考图不存在: data/char_01（character_refs）
```

集内所有分镜全灭，但文件明明存在。

**根因**

`data-schema.md` 规定 `shots.json` 的 `character_refs` / `scene_refs` 存的是**字典 key**（`char_01`），
真实路径登记在 `characters.json` / `scenes.json` 里。旧实现直接把 key 拼成 `data/char_01` 去查文件。

**改动**

```python
# main() 里，读到 shots/prompts 之后
REFS_MAP: dict = {}
for _name in ("characters.json", "scenes.json"):
    _d = load(DATA / _name, {}) or {}
    if isinstance(_d, dict):
        REFS_MAP.update(_d)
...
refs_all = [REFS_MAP.get(x, x) for x in refs_all]   # 未登记的 key 保留原值，便于报错定位
```

### P1-b 槽位数只数角色图（把「2 角色 + 1 场景」判成缺图）

**现象**

```
[FAIL] ep07_004: <Picture 3> 超出参考图槽位（当前 2 张）
```

**根因**

H3 的 6 个参考槽是「角色图 + 场景图」**按顺序共用**一套编号，`<Picture N>` 的 N 指合并后的序号。
旧实现只数 `character_refs`，凡是带场景图的镜头全部误判。

**改动**

```python
# 规则 6
-6. 参考图槽位一致性：len(character_refs) >= max(<Picture N>)
+6. 参考图槽位一致性：len(character_refs) + len(scene_refs) >= max(<Picture N>)
...
refs_all = list(s.get("character_refs") or []) + list(s.get("scene_refs") or [])
e, w = check_shot(sid, v["prompt"], v.get("duration"), refs_all, DATA)
```

**验证**

进门口禁对 E06–E17 全部 `[OK]`；故意删一条 refs 仍能报 FAIL（说明校验没被关掉）。

**回滚**：还原两处 `refs_all` 与规则 6 文本即可。**不建议回滚**，属纯 bug 修正。

## P2 · `pipeline.py`：出图节点的画幅值需要 value_map

**现象**

# build_image_node_list()
n = nodes.get("ratio")

-    pairs.append((n.get("nodeId"), n.get("fieldName"), ratio))
+    _vm = n.get("value_map")
+    _val = _vm.get(str(ratio), ratio) if isinstance(_vm, dict) else ratio
+    pairs.append((n.get("nodeId"), n.get("fieldName"), _val))

**验证**：`config.local.json` 的 `image_providers.banana.nodes.ratio.value_map` 配好后，
出图按 16:9 / 9:16 正确切分。

## P3 · `runninghub_client.py`：v2 提交通道 + 直链下载鉴权

### P3-a 提交只走 legacy 通道，拿不到 810 的可操作提示

**现象**

平台返回 `{"code": 810, "msg": "WORKFLOW_NOT_SAVED_OR_NOT_RUNNING"}`，只看到错误码，不知道要做什么。

**根因**

官方现行通道是 `POST /openapi/v2/run/workflow/{workflowId}`，错误字段是 `errorCode/errorMessage`；
旧实现只有 legacy `POST /task/openapi/create`，且把 810 当普通失败。

**改动**

1. 新增 `create_workflow_v2()`：body `{addMetadata, nodeInfoList, instanceType, usePersonalQueue[, retainSeconds]}`，
   识别 `errorCode`，并对 810 / 380 附可操作提示（去网页端「保存并运行一次」/ 核对编号）。
2. `create()` 里改为 **v2 优先**，仅当路由不存在（`code == 1001` 或 `invalid url`）才退回 legacy。
3. 新增 `_v2_route_missing()`：把「路由不存在」与「业务结论」分开，避免把 810 当兼容问题重试。

```python
if k in ("workflow", "wf", "comfy"):
    try:
        return await self.create_workflow_v2(str(target_id), node_info_list, instance_type)
    except RunningHubError as e:
        if not _v2_route_missing(e):
            raise
        return await self.create_workflow(str(target_id), node_info_list, instance_type)
```

### P3-b 产物直链下载 400（账号 3 的 .cn 站点）

**现象**

出片成功，但下载 `final.mp4` 时 `HTTP 400`；把同一 URL 用浏览器/curl 打开是 200。

**根因**

账号 3（.cn）的产物落在 `volces.com / TOS` 对象存储，**拒绝带 `Authorization` 或非浏览器 UA 的请求**。
旧实现无条件附 `Authorization: Bearer`。

**改动**

```python
host = (urlparse(url).netloc or "").lower()
headers = {"User-Agent": self._DOWNLOAD_UA, "Referer": self.base_url + "/"}
if "runninghub" in host:
    headers["Authorization"] = f"Bearer {self.api_key}"
```

**验证**：账号 3 出片后能正常落盘；账号 2（.ai）产物仍带鉴权。

## 11. 补充：把「封面首帧」加入拼接（2026-10-18 下午）

需求：每集第 1 帧必须是 9:16 的画布海报，海报原图为 3:4（896×1200）。

落点：`tools/cover_lib.py`（封面片段生成）+ `tools/ep01_stitch.py`（拼接时前置）+ `tools/add_cover.py`（回补已交付集）。

**两个必须记住的坑**

1) **不能用 mp4 concat demuxer 直接拼「封面 + 正片」**
   跨编码器混拼时总时长会被算成两倍（实测 78.4s → 153.1s）。
   正确做法是 **MPEG-TS 字节级中转**：两段各自 `-c copy -bsf:v h264_mp4toannexb -f mpegts` → 二进制拼接 →
   回封装 `-c copy -bsf:a aac_adtstoasc`。全程不重编码，正片零画质损失，耗时 <2s/集。

2) **单帧 `-loop 1` 输入直接接 `overlay`/`gblur` 链路，前 5 帧会从纯黑爬亮**
   滤镜链里并没有 `fade`，但实测首帧亮度 0.0 → 8.4 → 18.2 → 27.5 → 37.1 → 47.2，线性上升。
   这会让「首帧是海报」直接失效（用户看到的第一帧是黑场）。
   解法：**先合成一张静帧 PNG**（模糊底 + 居中海报 + 色彩范围转换），再用 `-loop 1` 把 PNG 编码成视频；首帧亮度恒定。

**画像细节（同样影响观感）**

- 原图是 JPEG（full range `yuvj420p`），成片是 `yuv420p` + `tv` 范围。
  不做 `scale=in_range=full:out_range=tv` 就整片发灰。
- 3:4 海报装 9:16 画布**不能裁切**（会切掉标题和底部字幕），
  采用「放大 40px 高斯模糊 + 压暗 12% 作背景，海报等比缩放居中」，标题与角标完整。

**验收口径**

```bash
# 首帧亮度应恒定（海报本身约 56），且不随帧号变化
ffmpeg -i <ep>.mp4 -frames:v 4 f_%02d.png
# 时长应为「正片 + 封面秒数」
ffprobe -v quiet -show_entries format=duration -of csv=p=0 <ep>.mp4
# 音画时长差 <0.05s
ffprobe -v quiet -show_entries stream=codec_type,duration -of csv=p=0 <ep>.mp4
```

## 12. 补充：批次目录同秒冲突（并发出片的隐蔽杀手）

**现象**

多账号并行出片时，`accountStatus` 显示在跑任务数为 0 或 1（看起来「账号空了」），但本地队列刚提交了 5 个任务，且没有 421。单段日志：

```
[ep29_003] ✗ 未捕获异常（已隔离，不影响其他分镜）:
  [Errno 13] Permission denied: '...\output\20261018_181534\state.json.tmp'
[driver] 本轮结束 用时 3s  exit=1
```

**根因**

引擎按 `%Y%m%d_%H%M%S`（秒级）创建批次目录。同一秒内启动的多个 `rh_ep_run` 进程会落进**同一个** `output/20261018_181534/`，
然后并发写 `state.json.tmp` —— Windows 上后到者直接 `Errno 13 Permission denied`，该段 3 秒内即失败。

后果：5 个并发里 4 个秒败，只剩 1 个真正提交到平台 → 后台看起来「空了」；更糟的是这些失败段会在 75 秒后
**同时重试**，继续撞同一把锁，形成稳定复现的死循环。

**建议的引擎侧修法（二选一）**

1. 批次目录名加进程标识：`%Y%m%d_%H%M%S_<pid>`（最小改动，彻底消除冲突）；
2. 写 `state.json` 用原子替换 + 独占重试（`open(tmp,'x')` / 捕获 Errno 13 后 sleep 抖动重试），
   并让 `state.json.tmp` 文件名带 pid。

**产线侧已落地的临时方案（`tools/pool_run.py`）**

```python
proc = subprocess.Popen(...)          # 启动单段
inflight[name].append((proc, shot))
log(...)
time.sleep(1.5)                        # ★ 强制错峰，保证跨秒建目录
```

**验证**：18:16:56 / 18:16:57 / 18:16:59 / 18:17:00 / 18:17:02 五次提交分别落在 4 个不同批次目录，无一例 Errno 13。

**附带注意**：进程被杀后，已提交到平台的任务会变成「孤儿」，仍占用车道约 2 分钟，
此时新提交会短暂收到 421 —— 属正常现象，等孤儿任务结束后重试即可，不要据此调低并发。

## 13. 补充：字幕对轴（把「估算」换成「识别」）

**为什么必须改**

最初按「台词从镜头起点 +0.3s 开始，在该镜窗口内居中」排轴。实测用户直接反馈「有的早
有的晚」——因为 H3 生成的音轨里，同一句台词在镜头内的位置差异很大：有的镜头先给动作、
台词在尾部才起；有的开口即说。任何固定偏移都必然错。

**正确做法（四步）**

1. **提音频**：`ffmpeg -vn -ac 1 -ar 16000 -c:a pcm_s16le` → WAV；
2. **词级识别**：`faster-whisper`（small，es，`word_timestamps=True`）；
3. **文本匹配**：把分镜里已知的每句台词，按词序列相似度（`difflib`）匹配到识别结果的
   **连续词窗口**，取首词/末词时间做字幕起止；相似度 < 0.55 时回退估算并告警；
4. **生成 ASS** 烧录（1080×1920，Arial Bold 56，白字黑描边 3.2，距底 420px 避开平台 UI）。

**四个必须避开的坑（按踩到的顺序）**

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **VAD 会重映射时间戳** | 同一句漂移约 0.9 秒 | `vad_filter=False`；靠镜头窗口约束搜索，不靠 VAD 去噪 |
| 2 | **PyAV 版本不兼容** | `av.open() got an unexpected keyword argument 'metadata_errors'` | 不让 faster-whisper 解码容器：先用 ffmpeg 落 WAV，再传 numpy 数组 |
| 3 | **西语数词不归一** | 「noventa y siete」识别成 `97`，相似度 0 → 回退 | 两侧都过 `numberize()`（tens + y + units → 数字） |
| 4 | **匹配窗口有容差** | 末句被吸到上一镜尾部，提前 2.3 秒 | 严格限制在本镜；越界按秒扣分（-0.35/秒），宁可回退也不跨镜 |

另外两条与字幕无关但影响时间轴的事实：
- 母版最前有 **1.5 秒封面**，所有字幕整体后移；
- 每镜真实时长 = 帧数补齐到 17 的倍数后的时长（10s→243 帧 = 10.125s），
  用 `max(5, round(秒*24))` 再补 17 的倍数即可，与母版实测误差 <0.05s。

**实测效果（E01，11 镜 / 13 句）**

- 平均文本相似度 **1.00**，回退 0 条（修正数词与窗口后）；
- 相对旧估算模型的位移：**+3.51s ~ −2.32s，均值 +1.4s** —— 正是「有的早有的晚」；
- 单集成本：识别 9–12s + 放大烧字幕 9s ≈ **20 秒**（CPU int8，small 模型）。

**建议的落地形态（SoloDrama）**

新增 `stages/production/scripts/align_subtitles.py`（本仓库 `tools/` 下已实现可移植版本）：
- 输入：`shots.json`（台词与时长）+ 母版 mp4；
- 输出：`.ass`（供烧录）与 `.srt`（供平台侧软字幕）；
- 配置项：`whisper_model`（tiny/base/small）、`style`（字号/描边/边距）、`offset`（整体位移，解决「习惯滞后半拍」）、`shot_window_strict`（是否严格限制在镜内）；
- 关键约束：**模型只加载一次**，批量处理时必须复用同一 `WhisperModel` 实例，否则每集多花 3–5 秒。

### 13.1 补记：md 与成片时间轴不一致时怎么办

**现象**：E17–E23 这七集在「重排分镜」之前就已出片，之后 md 被改成 13 镜 / 65 秒，
而成片实际是 14 镜 / 78 秒。用 md 推算窗口给字幕定位，整集错位。

**判断**：`|Σ(成片段时长) − Σ(md 计划时长)| > 1.5 秒` 即视为不一致。

**解法**：拼接时写进 `_norm672/<shot>/final.mp4` 的归一化段，就是母版的真实输入。
逐段 `ffprobe` 拿到时长、累加即可还原**成片真实镜头窗口**（含 1.5 秒封面偏移），
再用「每窗口最多认领 2 句台词」的方式分配。实测 E20 有 14 个窗口、md 只有 13 镜，
用真实窗口重排后，原来错位的那句（"Señor Zúñiga, nos vimos el mes pasado…"）
从 15.8 秒回到 38.0 秒，与 ASR 检出的语音位置一致。

**批量判定**：`windows_from_segments(ep)` 有结果且与 md 总时长差 > 1.5 秒时走真实窗口，
否则走 md 窗口。二者共用同一套「词级相似度 + 单调游标」匹配。

### 13.2 补记：断句与重叠（字幕可读性的三条硬约束）

1. **断点不落虚词**：`de / la / el / en / su / que / y / a / con / por / para / un / los / las / del / al / se / le / lo / mi / tu` 会读成断句（「de su | empresa」）。切分时若末词是虚词，回退一个词。加此约束后，落在虚词上的条数从 73 降到 52（其余是原句本身以虚词结尾）。
2. **优先句末标点**：若最后 30% 内出现 `. ! ? …`，在该标点后断开。
3. **防重叠**：同镜两句可能抢同一段语音，导致字幕互相压住。按起点排序后逐条夹紧（后一条起点 ≥ 前一条终点 + 0.03 秒），并把时长下限锁到 0.9 秒。

**性能补充**：识别结果按 `epNN.json` 缓存（词级时间戳，几十 KB/集）。改样式、改断句规则时只需重跑合成与编码，识别一次即可复用——重出 40 集的耗时从 15.8 分钟降到约 7 分钟。
