# 2026-10-22 · H3 参考图槽位「残留图」修复记录（V0.7.9）

> 用户报告：「调用 RH 的视频工作流时，如果里面默认打开了 6 张图片，这个项目会把原本留在里面的图片作为参考放进去」。
> 结论：**确有其事，而且比报告说的更重** —— 不只画面被污染，还是 OOM 的帮凶。

---

## 一、现象与证据链

### 1.1 工作流真实结构（只读接口实测）

`POST /api/openapi/getJsonApiFormat`（workflowId `2110380691388194818`）返回 31 个节点，其中：

| nodeId | class_type | 默认值 | 接到哪 |
|---|---|---|---|
| 137 | `LoadImage` | `cb955bf6….png` | `136.ref_images.ref_image_0` |
| 139 | `LoadImage` | `3fce2ed5….png` | `136.ref_images.ref_image_1` |
| **146** | `LoadImage` | `cb955bf6….png` | `136.ref_images.ref_image_2` |
| 159 | `LoadImage` | `cb955bf6….png` | `136.ref_images.ref_image_3` |
| **160** | `LoadImage` | `cb955bf6….png` | `136.ref_images.ref_image_4` |
| **161** | `LoadImage` | `cb955bf6….png` | `136.ref_images.ref_image_5` |

节点 `136` = `MiniMaxH3ReferenceToVideo`，六个 `ref_image_0…5`。

### 1.2 项目实际只覆盖几个

`<工作区>/config.local.json` 的 `h3.nodes`：

- `char_ref` → node **137**（1 个）
- `scene_ref.slots` → node **139**、node **159**（2 个）

**覆盖 3 个，未覆盖 146 / 160 / 161。**

### 1.3 根因：`nodeInfoList` 是覆盖表，不是完整表

`RunningHubClient.build_node_list()` 有一条 `if value is None: continue` —— 没有值的节点直接**不发**。
而平台的语义是：**没发的节点 = 沿用工作流里保存的值**。所以那 3 个槽位每镜都在送
`cb955bf6….png` 这张遗留图。

旧代码里还留着一句自我安慰的注释：

```
第 i 个参考图落到第 i 个槽位；参考图少于槽位时，后面的槽位**不发送**
（实测：不发 = 沿用工作流内置默认，安全，不会塞进多余角色）。
```

**「安全」这个判断是错的** —— 沿用默认 ≠ 空，而是「沿用上一次调试留在工作流里的图」。
本次已把这句注释删掉并写明原因。

### 1.4 连带的第二个后果：显存

`config.py` 的 `OOM_RETRY` 注释早就写着：

> 实测：12 秒镜头 + **6 路参考图** + 0.8MP，在 default(24G) 实例上采样阶段必挂

也就是说，模型一直在按 **6 路参考图** 做推理，其中 3 路是废物。顶掉之后参考图降到 3 路，
显存压力与采样时间都会下降 —— 这条属于副产品，但对出片稳定性是正向的。

## 二、修复

### 2.1 核心：提交前把「未使用槽位」显式顶掉

新增 `pipeline.py` 的槽位卫生模块：

| 函数 / 类型 | 作用 |
|---|---|
| `is_image_slot(node)` | 认图片槽：`LoadImage*` 类节点，或 AI 应用通道里 fieldName 为 `image` / `image1` / `image_6` / `imageUrls` |
| `image_slot_nodes(nodes)` | 从 `get_nodes()` 结果里挑出全部图片槽（按 nodeId 去重） |
| `covered_slot_ids(nodes_cfg)` | 配置里声明的槽位集合（单节点 `nodeId` 与 `slots[]` 两种形态都算） |
| `placeholder_png(path)` | 生成 1024×1024 中性灰占位图（幂等，已存在就复用；纯色 PNG 仅 5.3 KB） |
| `SlotGuard` | 处置计划：`unused` / `ghost` / `fill_pairs()` / `summary()` |
| `make_slot_guard(ctx, spec, nodes_cfg, kind, target_id, cache_dir, ...)` | 探测 → 比对 → 备好占位图，运行开始时构建一次，全 shot 共用 |

`build_h3_node_list()` 与 `build_image_node_list()` 都新增 `slot_fill` 参数，把未使用槽位的
填充三元组追加进 `pairs`。

### 2.2 三种处置模式（`unused_slots.mode`）

| mode | 行为 | 适用 |
|---|---|---|
| **blank**（默认） | 上传中性灰图填进未使用槽位 | 常规；绝不带入残留图 |
| `empty` | 传空字符串 | 省一次上传。**风险**：ComfyUI 的 `LoadImage` 会把 `""` 当文件名 → `Invalid image file` |
| `keep` | 保留工作流默认 | **危险**，必须写 `reason`；只在确知残留图无害时用 |

`mode=keep` 缺 `reason` 时：`make_slot_guard` 直接抛错（退出码 4）；`config._validate_slots`
在配置层先警告并回退 `blank` —— 两道都不许静默放行。

### 2.3 值形态：默认 url（这是有实证的选择）

上传接口同时返回 `fileName`（`openapi/<sha256>.png`）与 `download_url`。
代码注释里曾说「`LoadImage.image` 要文件名不是 URL」，但**项目历史 30 集的实证相反**：

```
07-成片/20261021_203211/ep01_sc01/refs_used.json
  characters submitted = https://rh-hk-images-switch.xiaoyaoyou.com/input/openapi/81b86ea1…
  scenes     submitted = https://rh-hk-images-switch.xiaoyaoyou.com/input/openapi/622ffd56…
```

30 集就是传 URL 出的片。所以 `value_form` 默认 `url`（跟既有做法一致），`fileName` 留作
只认文件名的工作流切换用。两种值都预先备好，切换只改配置。

### 2.4 顺带修掉的三处

1. **`build_node_list` 去重**：按 `(nodeId, fieldName)` **先到先得**。以前同一槽位发两次平台行为未知。
   先到先得保证「真实参考图永远赢过填充值」。
2. **`empty` 模式的空字符串不被误丢**：`if value is None` 只挡 `None`，`""` 放行 —— 那是有意发送的空值。
3. **`h3.nodes` 补上结构校验**：overlay 里原来只校验 `image_providers.*.nodes`，H3 侧漏了。

### 2.5 可观测性（事故里「没人发现」才是真问题）

- 运行开始时打印：`图片槽位：工作流 6 个 ｜ 本项目覆盖 3 ｜ 未使用 3` + 具体 nodeId 与处置动作
- `--dry-run` 逐条打印「预演：[h3] 槽位 160（LoadImage）将被顶掉，原默认=cb955bf6…」
  —— 预演不联网，靠真实运行落下的 `slots_<key>.json` 快照；没有快照就明说没预演到，不假装做过
- `--probe` 每行标注「图片槽·已覆盖 / 图片槽·未使用（提交时填占位图顶掉）」，末尾给合计
- 探测失败不静默：打印「本轮只按配置发送，未使用的槽位会沿用工作流里保存的图」
- `ghost` 检测：配置指向工作流里不存在的 nodeId 时告警（工作流被改过的信号）

## 三、验证

| 项 | 结果 |
|---|---|
| 新增 `engine/tests/test_slot_hygiene.py` | **32/32 通过**（槽位识别 5 / 覆盖判定 2 / 占位图 3 / 填充策略 6 / 提交列表 4 / 配置校验 6 / 探测与预演 6） |
| 全量离线回归 | **678 例，0 失败** |
| 真实工作流 dry-run | `工作流 6 个 ｜ 覆盖 3 ｜ 未使用 3`；`nodeInfoList` 里 160/161/146 变成 `slot_blank_1024.png`，`cb955bf6….png` **完全消失** |
| `--probe` 实测 | 6 个 LoadImage 逐行标注，合计 `6 / 3 / 3` |
| 占位图上传 | 成功，`fileName=openapi/53f46d3d….png`、`download_url=https://rh-hk-images-switch…`、5334 bytes |
| **真实提交出片** | ❌ **未完成** —— 平台返回 `errorCode=605 Your balance is insufficient`（账号余额不足） |

**关于最后一项，必须说清楚**：方案在「提交前的产物」上已经完全验证（nodeInfoList 内容正确、
占位图能上传、值形态有 30 集实证），但**没有跑通一次真实出片**来证明
「MiniMaxH3ReferenceToVideo 收一张纯灰参考图时正常出片」。这是唯一的残留不确定性。

风险评估：中性灰是无信息量输入，模型对它做 reference conditioning 不会产生具体人物/景物；
比「一张别人的人脸」安全得多。但**要真正确认，需要账号充值后跑一镜**：

```bash
python main.py --workspace "<ws>/video-pipeline" --video-only --only ep01_sc01 --limit 1
```

如果这一镜出来画面正常、且 `usage.consumeCoins` 在 31–34 区间，即为完全确认。
若报图像相关错误，把 `unused_slots.mode` 改 `empty`（传空）或 `value_form` 改 `fileName` 再试。

## 五、给后续的人

1. **新建/另存工作流后，先跑 `--probe`**。它会直接告诉你「几个图片槽、覆盖几个、剩下几个会被顶掉」。
   如果未使用数量和你预期不符，说明 `nodes` 映射漏了。
2. **不要为了「少发点参数」把 `unused_slots` 关掉**。省下的那点流量，换来的可能是「画面里突然多个人」，
   而这种错**在成片里才看得出来**，返工成本是整集。
3. 老项目不需要迁移：`discover=true` 是运行时探测，配置里不用预先写 nodeId。
4. 如果哪天真要保留工作流的默认参考图（比如工作流本身就带风格参考图），用
   `mode=keep` + `reason`，**把理由写清楚** —— 半年后接手的人需要知道为什么可以。
