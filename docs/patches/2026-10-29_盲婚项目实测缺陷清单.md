## 1. 阻断级

### D1 · dry-run 把已完成分镜重置为 `PENDING`，导致下一次真实运行重复扣费

> **状态：已修（2026-10-29 23:55）**，验证见本节末「已验证」。

**现象**

批次 `20261029_231210` 在 23:15:49 完成 `shot_001`（`final.mp4` 已下载、`video_url` 已存、`consumeCoins=43` 已记）。
23:30:11 跑了一次 `--dry-run` 做预演；之后 `--resume --dry-run` 显示「待处理 **8** 个分镜」，
而实际只应剩 7 个。`state.json` 里 `shot_001.video_status` 已从 `SUCCESS` 变回 `PENDING`。

也就是说：**只要在出片后跑过一次 dry-run，下一次 `--resume` 会把已付费的段重新提交一遍。**

**根因**（两处叠加）

`engine/pipeline.py:1076` —— 跳过判定把 dry-run 排除在外：

```python
final_mp4 = sdir / "final.mp4"
if (not ctx.dry_run and state.get("video_status") == ST_SUCCESS and final_mp4.is_file()):
    ctx.log(f"[{shot_id}] ✓ 视频已存在，该分镜全部完成，跳过（不再重复上传参考图）")
    return ST_SUCCESS
```

`engine/pipeline.py:1147-1151` —— dry-run 分支无条件把状态写回 `PENDING`：

```python
if ctx.dry_run:
    node_list = _nodes_for(h3.get("duration"))
    ctx.log(f"[{shot_id}] ⑤ [DRY-RUN] H3 nodeInfoList = ...")
    await ctx.state.update(shot_id, video_status=ST_PENDING)   # ← 无条件覆盖
    return ST_PENDING
```

**修法**

1. dry-run 分支**不写** `video_status`，只写日志：

```python
if ctx.dry_run:
    node_list = _nodes_for(h3.get("duration"))
    ctx.log(...)
    return ST_PENDING          # 不再 state.update
```

2. 跳过判定与 dry-run 解耦：dry-run 也应识别「已完成」并打印「将跳过」，否则预演金额永远偏高：

```python
already_done = state.get("video_status") == ST_SUCCESS and final_mp4.is_file()
if already_done:
    ctx.log(f"[{shot_id}] ✓ 已完成{'（dry-run 仅预览）' if ctx.dry_run else '，跳过'}")
    return ST_SUCCESS
if ctx.dry_run:
    ...
```

**验证**

```bash
# 1) 跑到一段成功，记录 state.json 的 updated_at
# 2) 跑一次 dry-run
python stages/video/workflow/scripts/run.py --resume <batch> --video-only --dry-run --data-dir "../06-提示词"
# 3) 断言：state.json 的 updated_at 未变、shot_001.video_status 仍为 SUCCESS
```

**已发生的代价**：本次靠手工把 `state.json` 改回 `SUCCESS` 才避免重跑，否则白烧 43 币。

**已验证（修复后）**

8 段全 SUCCESS 的批次上再跑一次 `--resume --dry-run`：

```
[shot_001] ✓ 视频已存在，该分镜全部完成，跳过（不再重复上传参考图）（dry-run 预览，未改状态）
state.json → 8 段 video_status 仍全部 SUCCESS
summary.json → success 8 / pending 0
```

注意：`state.json` 的 `updated_at` 仍会变（前置的 image/crop 阶段会写状态），但 `video_status` 不再被污染——
判断是否安全看 `video_status` 与 `summary.totals.pending`，不要看文件 mtime。

### D2 · `refs.json` 结构不符合契约时静默降级为 0 条

**现象**

把 `04-资产/refs.json` 写成扁平字典（`{"char_01": "D:/.../char_01.png", ...}`）后，
`convert_storyboard.py --apply` **不报错**，但写出的 `characters.json` 是 `{}`。
随后出片日志显示「参考图匹配完成（角色 0 张）」，成片完全没有人物锁定。

**根因**

契约要求嵌套结构，读取端不校验顶层键：

```json
{ "characters": { "char_01": "/abs/path.png" }, "scenes": { "scene_01": "/abs/path.png" } }
```

`convert_storyboard.py` 的 `_load_refs()` 直接 `d.get("characters")`，取不到就返回空字典继续跑。

**修法**

```python
def _load_refs(p: Path) -> dict:
    d = json.loads(p.read_text(encoding="utf-8"))
    if not isinstance(d, dict):
        raise SystemExit(f"[FAIL] {p.name} 顶层必须是对象")
    if "characters" not in d and "scenes" not in d:
        # 扁平结构：按 key 前缀自动分组，并打印一次提示
        chars = {k: v for k, v in d.items() if k.startswith("char_")}
        scenes = {k: v for k, v in d.items() if k.startswith("scene_")}
        if not (chars or scenes):
            raise SystemExit(f"[FAIL] {p.name} 既无 characters/scenes 分组，也无 char_*/scene_* 前缀")
        print(f"[WARN] {p.name} 为扁平结构，已按前缀自动分组（characters={len(chars)} scenes={len(scenes)}）")
        return {"characters": chars, "scenes": scenes}
    return d
```

**验证**：故意写一个扁平 `refs.json`，转换器应打印 WARN 且 `characters.json` 条目数 > 0。

### D3 · `scene_ref` 未配槽位时场景参考图被静默丢弃

> **状态：已修（2026-10-29 23:56）**，验证见本节末「已验证」。

**现象**

配置里只给了 `h3.nodes.char_ref.slots`（6 个槽）。`shot_001` 有 2 张参考图（`char_01` + `scene_01`），
干跑实际只发出 1 张：

```
nodeInfoList = [
  {"nodeId": "138", ... 提示词 ...},
  {"nodeId": "282", "fieldName": "image", "fieldValue": "[将上传] ...char_01_ValeriaSarmiento_00.png"},
  {"nodeId": "132", "fieldName": "value", "fieldValue": "6"}
]
```

`scene_01` 消失了。日志仍打印「参考图匹配完成（角色 1 张 / 场景 1 张）」，看起来正常。

**根因**

`engine/pipeline.py:1089-1097` 分别解析 `char_ref` 与 `scene_ref`，但槽位填充只按各自配置的 slots 消费；
`scene_ref` 没配 `slots` 时 `scene_values` 有值却无处可放，直接丢弃。

三个可选键的语义也没有定义清楚，实测结果：

| 配置键 | 实测行为 |
|---|---|
| `char_ref.slots[]` | 按数组顺序填，可用 ✅ |
| `scene_ref.slots[]` | 未配则不填（**静默丢弃**） |
| `image` | 实测「一张都没发」 ❌ |

**修法**（建议二选一，推荐 A）

A. **槽位池 + 顺序填充**：把所有角色图与场景图按 refs 顺序拼成一个列表，依次填进 `slots`；
   数量超出槽位时报 WARN 而不是静默截断。

B. **显式校验**：启动时检查 `len(char_ref.slots) + len(scene_ref.slots) >= 工作流图片节点总数`，
   不足直接 `[FAIL]`；`image` 键要么实现要么从文档删除。

**本次绕过方式**（工作区侧，不改引擎）：

```python
# 06-提示词/shots.json：把所有场景图并进 character_refs，scene_refs 置空
# 06-提示词/characters.json：并入 scenes.json 的条目
```

**验证**：任意含「角色 + 场景」两张参考图的分镜，`nodeInfoList` 里应出现 2 个不同 `nodeId` 的 image 项。

**已验证（修复后）**：数据恢复为标准结构（`character_refs=[char_01]` / `scene_refs=[scene_01]`），
干跑 `shot_001`：

```
[shot_001] ④ 参考图匹配完成（角色 1 张 / 场景 1 张）
nodeInfoList = [..., {"nodeId":"282", "fieldValue":"...char_01..."},
                      {"nodeId":"285", "fieldValue":"...scene_01..."}, ...]
```

修复前该处只有 `282` 一项。日志同时会打印
`[i] scene_ref 未配槽位，N 张场景图已并入 char_ref 槽位（共 X/Y）`，
超出槽位时改为 `[WARN] 参考图 N 张 > 可用槽位 M 个，超出部分未发送`（不再静默）。

### D7 · `prepare_refs.py` 硬编码 `<ws>/data`，新布局下直接报「找不到工作区」

**现象**

```bash
python stages/production/scripts/prepare_refs.py --workspace "D:/剧本/海外剧/4"
# [FAIL] 找不到工作区 data/：D:\剧本\海外剧\4
```

实际 `data` 在 `06-提示词/`。

**状态**：**已在本次修复**（引擎侧唯一改动）。

**修法**（已落地）

新增 `_data_dir(workspace)`，按 `layout.json` 的 `data_rel` 解析，读不到时回退 `data/`：

```python
def _data_dir(workspace: Path) -> Path:
    lay = workspace / "layout.json"
    if lay.is_file():
        try:
            rel = (json.loads(lay.read_text(encoding="utf-8")) or {}).get("data_rel")
            if rel and (workspace / rel).is_dir():
                return workspace / rel
        except (OSError, json.JSONDecodeError):
            pass
    return workspace / "data"
```

`collect_sources()` 与相对路径解析、`data/` 存在性检查三处改为使用该函数。

**回归风险**：`prepare_refs.py` 依赖 `characters.json`，而该文件在 S5 才生成；
S4 阶段跑会得到空列表。建议加一条明确提示：「S4 请用 refs.json，S5 后再跑瘦身」。

### D8 · 站点错配：余额接口两站都通，上传接口才报「API Key 不存在」

**现象**

zh 站签发的 Key（余额 24,856 币）在 `.ai` 站上：

| 接口 | `.cn` | `.ai` |
|---|---|---|
| `POST /uc/openapi/accountStatus` | 通过，24,856 币 | **也通过，同一账户** |
| `POST /openapi/v2/media/upload/binary` | 通过 | `{"code":1,"msg":"ApiKey verification failed: API Key不存在"}` |

错误信息把所有线索都指向「Key 无效」，但实际上 **Key 完全有效，只是站点不对**。

**根因**（三层叠加）

1. `engine/config.py:54` 默认 `https://www.runninghub.cn`；
2. **用户级环境变量** `RUNNINGHUB_BASE_URL=https://www.runninghub.ai` 长期存在（`[Environment]::GetEnvironmentVariable(...,'User')` 可查），优先级高于默认值；
3. `project-setup.json` 的 `site` 字段也写死 `.ai`，共 3 处。

三层都指向 `.ai`，而工作流 `2113319585146560513` 属于 zh 站。

**修法**

1. 在 `run.py check` 里加一致性校验：探一次 `GET /openapi/v2/workflow/{id}` 或上传探测，
   失败且错误含 `API Key不存在` 时，提示「请确认 base_url 与 workflowId 是否同一站点（.cn / .ai）」；
2. `drama.py setup --site` 写入 overlay 的 `runninghub_base_url`（而不是只写 `project-setup.json`）；
3. 文档里明确：环境变量会覆盖默认站点，多项目共存时**不要用全局环境变量**，改用项目 overlay。

**本次绕过方式**：在 `video-pipeline/config.local.json` 写入

```json
{ "runninghub_base_url": "https://www.runninghub.cn" }
```

实测 overlay **优先于** 用户环境变量，写入后上传立即通过。

**传染性验证**：本次为放大环节新写的 `tools/upscale_rh.py`，第一版把 `--base` 的默认值写成
`os.environ.get("RUNNINGHUB_BASE_URL") or DEFAULT_BASE`，干跑立刻又落回 `.ai`。
改成硬编码 `.cn` 默认后才正确。说明这个坑不是「配错了」，而是**默认继承路径本身就有害**——
工具应当默认取站点无关的安全值，把 env 作为显式 opt-in。

### D9 · H3 提示词的机器标记格式没有文档，写错只 WARN

**现象**：三种写法都被 `ingest_check` 判为不合规，但 `--apply` 照写不误：

### D25 · `--concurrency` / `--batch-size` 的 argparse 默认值早于覆盖层求值，配置被静默忽略

> **状态：已修（2026-10-30 00:32）**，验证见本节末。

**现象**

`video-pipeline/config.local.json` 里写入 `"concurrency": 5`，`C.CONCURRENCY` 确实是 5，
但实际跑批始终只提交 2 个任务。观察 `inflight.json` 与 `state.json` 的 `video_task_id`：

```
在途数 2
  shot_004 2026-10-30 00:22:32
  shot_007 2026-10-30 00:23:54
（其余 4 段没有 task_id —— 还没提交）
```

任务是严格「一波 2 个」推进的，就是内置默认值。

**根因**

```python
# main.py:813（build_parser，模块加载期执行）
p.add_argument("--concurrency", type=int, default=C.CONCURRENCY, ...)   # ★ 此刻 C.CONCURRENCY 还是 2
```

执行顺序是：

1. `build_parser()` —— 这时 `config.local.json` **还没加载**，`default` 被固化成 2；
2. `parse_args()` —— `args.concurrency = 2`；
3. `_bootstrap(args)` —— 才 `apply_overlay()`，`C.CONCURRENCY` 变成 5，但 `args.concurrency` 已经是 2；
4. 调度用 `args.concurrency`（不是 `C.CONCURRENCY`）。

**更阴的一点**：日志 `main.py:533` 打印的是 `C.CONCURRENCY`，显示「并发=5」，
而真实调度是 2 —— **日志在说谎**，比直接报错更难查。

**修法（已落地）**

1. 两个参数的 `default` 改为 `None`；
2. `_bootstrap()` 在 `apply_overlay()` 之后补：

```python
if getattr(args, "concurrency", None) is None:
    args.concurrency = C.CONCURRENCY
if getattr(args, "batch_size", None) is None:
    args.batch_size = C.BATCH_SIZE
```

**已验证（修复后）**

```python
args = build_parser().parse_args(["--check"])
_bootstrap(args)
# args.concurrency = 5 | args.batch_size = 20 | C.CONCURRENCY = 5
```

**同类风险**：凡是 `build_parser()` 里写 `default=C.XXX` 的参数，都会在 overlay 之前固化。
建议全库排查一遍（`grep -n "default=C\." engine/*.py`），统一改成「default=None + bootstrap 补值」。

### D26 · 任务 FAILED 时错误信息只有「工作流运行失败」，真实原因被丢弃


完全看不出是内容问题、参数问题还是资源问题。重试还是放弃？无从判断。

**真实原因（手动查 `/openapi/v2/query` 才看到）**

```json
{"status": "FAILED", "errorCode": "805", "errorMessage": "工作流运行失败",
```

即**平台侧 GPU 显存不足**，属于资源类瞬时错误：**不计费、可直接重试**（本次重试成功）。

```python
fr = payload.get("failedReason") or {}

if fr.get("exception_type"):
    hint = f"｜{fr['exception_type']} @ {fr.get('node_name')}"
raise RunningHubError(f"H3 视频 返回 FAILED: {payload.get('errorMessage')}{hint} ...")
```

| `exception_type` | 含义 | 处置 |
|---|---|---|
| `torch.OutOfMemoryError` | 平台显存不足 | **直接重试**，不计费；高并发时更易出现（本次是 5 并发同时跑 8 段时出现的） |

| 7 | RunningHub Deepcleaner | `model_action` | `Purge Model` |

**两点必须知道**：

1. **放大引擎不是 Topaz**，是 `RH_Astra`（Iris 模型）。文档与命名需与实际一致，否则后续排查会被名字带偏。
2. **输出尺寸会按源宽高比吸附**：源 672×1216（0.5526）传 1080×1920 后输出 **1062×1920**，
   宽度不是目标值。要交付精确 1080×1920 必须二次补正：

```bash
ffmpeg -i raw.mp4 -vf "scale=1080:1920:flags=lanczos" -c:v libx264 -crf 17 -pix_fmt yuv420p -c:a copy out.mp4
```

**成本实测**：61 秒整集一次放大 = **35 RH币**（0.8MP → 1080×1920），耗时 174 秒，产出 50MB / 6.7Mbps。

### G2 · 没有「单段重跑」

`run.py` 只有 `--limit N`（从头数）与 `--resume`（全量补齐）。
要重跑第 5 镜只能手工改 `state.json` 的 `video_status`。

**建议**：加 `--only shot_005` / `--shots shot_003,shot_005`，
实现上等价于「把指定段的状态重置为 PENDING，其余段视为已完成」。
