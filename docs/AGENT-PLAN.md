# 全自动出片 Agent：方案

> 目标：在 WebUI 上给一次「跑这一集」，它自己走完导入 → 出图 → 分镜图 → 出片 → 剪辑 → 发行，
> 只在**必须人决定**的地方停下来问你。当前状态是「每一步都能点，但要人一步步点」，
> 本方案要补的是**编排层**，不是再造一套引擎。

## 一、先定义「全自动」的边界

「全自动出片」有三种理解，必须先分清，否则做出来的东西没人敢用：

| 理解 | 含义 | 本方案 |
|---|---|---|
| A. 无人值守 | 点一次，人可以走开，回来拿成片 | **追求这个**，但受 GPU 时长限制（见 §6.1） |
| B. 无人决策 | 质量、风格、钱都由模型自己定 | **不做**。选镜、改提示词、花钱必须有人点头 |
| C. 无人工操作 | 不用敲命令，但可以点按钮 | 现状已接近，不是目标 |

所以本方案的验收口径是：

> 一次点击 → agent 自主推进 → 遇到「三类闸门」停下问你 → 回答后继续 → 产出 `09-发行/剧集/EpisodeNN.mp4`。
> 中途不需要人回忆「下一步该点哪个按钮」。

「两类闸门」：**批量**（一集以上）、**改内容**（提示词/换参考图）。
出图出片默认走本机，默认路径上没有按次计费的动作。要计费的通道（RunningHub）必须显式选，
选了才进计费闸门。本地跑则有**时间闸门**：一集要占几小时，
整季要占几天，这个量级的等待必须由人决定「现在开跑还是排到夜里」。
其余全部自动。

## 二、现状与差距

| 环节 | 现在 | 缺什么 |
|---|---|---|
| 流程状态 | `nodes.py` 12 节点状态机，只读磁盘 | 缺「循环执行」的驱动 —— 现在靠人 `next` 一次 `do` 一次 |
| 执行 | 每个节点有独立脚本，能单独跑 | 缺统一的「下一次重试换什么」策略 |
| 判定 | 每个节点有机器判据（退出码 0/2/3/4） | 判据不过时，谁来修、修什么，全靠人 |
| 成本 | `cost_model` 能预估，`cost_ledger` 能记账 | 缺「预授权额度」——现在每笔都要确认 |
| 界面 | Studio 能触发单个动作、看单次日志 | 缺「一次运行」的视图：进度、卡点、产物墙 |
| 断点 | 各脚本自带跳过逻辑 | 缺统一的 journal：跑到哪、为什么停、重开怎么接 |

**一句话**：引擎的零件齐了，缺一条把所有零件串起来并按规则自动走的流水线，以及一个能看见它的界面。

## 三、架构

三层，边界清晰，任何一层可单独替换：

```
┌─────────────────────────────────────────────────────────────┐
│  WebUI（Studio）                                             │
│  Run Console 页：任务定义 ｜ 实时进度 ｜ 卡点批准 ｜ 产物墙     │
└───────────────────────┬─────────────────────────────────────┘
                        │ HTTP + SSE（现有 /api/run、/api/jobs 扩展）
┌───────────────────────▼─────────────────────────────────────┐
│  Agent Runner（新增：web/core/agent/ 或 stages/agent/）       │
│                                                              │
│  Supervisor   读 nodes.py 状态机 → 决定下一个节点             │
│  Executor     跑命令 / 调 LLM（用现有 commands.py 的声明）      │
│  Critic       判据不过 → 生成修复方案（最多 3 次，每次换变量）  │
│  Budget       钱与时间的闸门（预估 → 预授权 → 记账）            │
│  Journal     每步落盘（.agent/journal.jsonl），重启可续          │
└───────────────────────┬─────────────────────────────────────┘
                        │ 与现在完全相同：subprocess + data/ 契约
┌───────────────────────▼─────────────────────────────────────┐
│  引擎（不改）：stages/import · assets · video · subtitle      │
└─────────────────────────────────────────────────────────────┘
```

**关键：Runner 不碰引擎内部。** 它只会「跑命令 + 读产物 + 按判据判断」，
和现在 `drama.py` 做的事一模一样，只是把「人读 next 再点」换成「循环读 next 自动跑」。

## 四、四条核心设计决策

### 4.1 流程由确定性状态机定，不由 LLM 定

`nodes.py` 的 12 节点已经写好「谁读谁、判据是什么、不过能回哪」。
Runner 的 Supervisor 只做一件事：`while True: node = next(); run(node); check(node)`。

LLM 只在**一个局部**出现：`Critic` —— 判据不过时，读错误日志与产物，产出「这次改什么」
（换一个 aspect、降 mp、换一张参考图、把 duration 拆成两镜）。而且要求每次修复**必须变一个变量**，
否则判 `stuck` 停下（这条规则 `nodes.py` 里已有，直接复用）。

理由：让模型决定流程，跑三次三个结果，出问题无法复现，也没法向人解释「为什么它跳过了出图」。

### 4.2 人是闸门，不是操作员

把「要人做的事」从「点按钮」改成「批队列」：

```
待批准队列
├ [批量] 整季 30 集将连续运行（预计 76 小时）           [批准] [先跑 1 集] [排到夜里] [取消]
├ [时间] 本集 8 镜约 2.5 小时，现在跑还是排夜里？        [现在跑] [排到 23:00] [只跑 1 镜]
└ [改内容] shot_007 连续 3 次质量不过：首帧黑屏         [看首帧] [改提示词] [标记废弃]
```

一次批准可以覆盖一批（比如「本集所有重跑都批」），而不是每镜弹一次。

### 4.3 断点即真相：Runner 不存内存状态

每一步写一行 journal：

```jsonl
{"t":"2026-11-04T01:20:11","node":"asset.render","ok":true,"detail":"6/6 张","wall_s":312}
{"t":"2026-11-04T01:25:40","node":"board.frame","ok":false,"detail":"缺 shot_007","attempt":1,"fix":"换 aspect 9:16"}
```

重启后只读 journal + 磁盘，不依赖进程内存。理由：本地出片是小时级任务，
浏览器关掉、机器重启、ComfyUI 崩掉都是常态。

### 4.4 质量判定只做「机器能判」的部分

自动判据（全部可机器复算）：

| 检查 | 判据 | 不过怎么办 |
|---|---|---|
| 产物存在 | `final.mp4` 且 > 10KB | 重跑 |
| 时长 | 与 `h3_prompts.duration` 差 ≤ 1s | 重跑（可能被截断） |
| 首帧 | 与分镜图的感知哈希距离 < 阈值 | 报警（构图跑偏） |
| 黑帧 | 抽 3 帧，平均亮度 > 阈值 | 重跑 |
| 音轨 | `ffprobe` 有 audio stream | 报警（H3 音轨来自 audio_vae） |

「这条能不能用」是审美，不自动判 —— 改成**快审**：一集跑完给 8 张缩略图，
人点「过 / 废」，废的那镜自动进重跑队列。一次 30 秒，比逐条看视频快一个量级。

## 五、分期与交付

### P0：能跑通的最小闭环（约 1 天）

| 交付 | 内容 |
|---|---|
| `stages/agent/runner.py` | CLI：`python -m stages.agent.runner --ws <ws> --ep ep01`，循环 12 节点直到 release |
| `stages/agent/journal.py` | jsonl 追加 + 断点恢复 |
| 复用 | `nodes.py`（状态机）、`commands.py`（命令声明与 argv 构造）、`cost_model`（预估） |

验收：一条命令跑完一集（本地通道），中途 Ctrl-C 再跑能续上，`09-发行/剧集/Episode01.mp4` 存在。

### P1：WebUI 全自动（约 2–3 天）

| 交付 | 内容 |
|---|---|
| `web/core/agent_runner.py` | 把 runner 挂到 FastAPI，后台线程跑，WebSocket/SSE 推进度 |
| `web/ui/studio/views/run.js` | Run Console：任务定义卡 / 阶段进度条 / 实时日志 / 卡点批准 |
| `web/app.py` | `POST /api/agent/run`、`GET /api/agent/status`、`GET /api/agent/stream`、`POST /api/agent/decide` |
| 产物墙 | 复用现有 `/media` 与 artifacts 白名单，按集聚合图/视频/成片 |

验收：在浏览器里点「跑这一集」，不碰命令行，出片后能在产物墙点开播放。

### P2：质量与成本可控（约 3–5 天）

| 交付 | 内容 |
|---|---|
| `stages/agent/qa.py` | 上表五项机器判据 + 首帧感知哈希 |
| `stages/agent/triage.py` | 失败归因：OOM / 节点类缺失 / 模型文件缺 / 提示词问题 / 参考图错 → 给具体修法 |
| 快审页 | 8 张缩略图 + 过/废，废的进重跑队列 |
| 预算 | 「这一集预计 40 分钟 / ￥0」在开跑前给出，超预算停下问 |

### P3（可选）：从 Skill 到成片一条命令

`skill 导入 → pack 校验 → 转换 → 全自动跑` 串成一条，即真正的「一句话到成片」，
但创作仍由外部 Skill 完成。

## 六、风险与对策

### 6.1 本地出片是小时级，不是分钟级

单镜 5–10 分钟（4060 8G + H3 10 步）。一集 8 镜 ≈ 1 小时，30 集 ≈ 30 小时。

对策：
1. **先小样**：每集默认只跑 1 镜，人确认画质与风格后再放全量（这条规则引擎里已有，Runner 要沿用）。
2. **夜间队列**：Runner 支持「排队到 N 点开始」，避开白天用机。
3. **并发只能是 1**：8G 卡两个任务必 OOM。所以提速只能靠「减少重跑」，不能靠并发。

### 6.2 ComfyUI 不是为长任务设计的

队列被打断、浏览器关掉导致任务中断、模型换显存策略都会让任务卡住。

对策：`submit_and_wait` 有超时；Runner 把「超时」当**可重试**而非失败，重试前先检查 ComfyUI `/queue` 是否还在跑同一 prompt_id。

### 6.3 质量不可自动判定

见 §4.4。方案是快审，不是假装能自动判。

### 6.4 一集 8 镜的提示词可能是同一套模板生成的

本地 H3 对提示词的敏感度很高。同一个 `video_prompt` 模板跑 8 镜，
可能出现「8 个镜头长得一样」。这一点要等首集真跑后才知道，方案里先留观测点：
出片后自动算 8 个首帧的相似度，过高就报警。

## 七、需要你拍板的四件事

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | 首次真跑用多长的镜？ | 4 秒 / 6 秒 / 12 秒 | **4 秒**：验证链路，10 分钟内出结果 |
| 2 | 快审的粒度 | 每集 8 张缩略图 / 每 4 集一批 / 只看出片失败的 | 每集 8 张 |
| 3 | 整季队列是否要「到点自动开跑」 | 要 / 不要 | 要（否则 30 小时必须人守着） |

## 八、不在本方案范围内

- 创作（选题/剧本/分镜/提示词）：仍在外部 Skill，引擎不做。
- 发布（上传平台）：`release_export` 只导出文件，不碰平台接口。
- 多机分布式：单机 8G 是当前硬件事实，做分布式等于换硬件。
