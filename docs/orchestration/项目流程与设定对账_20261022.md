- 目的：把「一条片子从选题到发布」的**实际流程**画清，并逐层核对**设定之间有无互相矛盾**。
- 方法：以 `stages/` 的代码为裁判，逐个真源交叉比对（代码 ↔ 配置 ↔ 文档 ↔ 在跑项目实例）。
- 结论：**流程本身是通的**，但有 **4 处真冲突**（会误导执行或导致错误判定）已就地修掉，
  **8 处口径不一致**（能跑但会看错）已改文档/配置，**1 处命名撞车**保留但标注清楚。

三条贯穿全线的约束：

1. **顺序不可调**：`workflow.py check --stage S<N>` 前置未完成 → 退出码 **4**；

## 二、五层真源，谁是裁判

| 层 | 位置 | 裁判权 |
|---|---|---|
| **代码** | `stages/**/scripts/*.py` | **最高**。文档与配置冲突时以代码为准；代码与用户意图冲突时先问用户 |
| **配置** | `<ws>/config.*.json`、`project-setup.json`、`style-plan.json`、`model-plan.json` | 项目实例级；同一份配置被多处读取，改一处即全局生效 |
| **文档** | `docs/orchestration/标准作业流程.md`（11 环节真源）、`docs/**` | 对**人**承诺的契约；必须与代码同步，否则是最容易骗人的一层 |
| **记忆** | `.workbuddy/memory/MEMORY.md` | 跨会话经验，**不是**规格；与本仓库冲突时以仓库为准 |
| **实例** | `D:/剧本/海外剧/2` 的 `*-state.json` / `*-plan.json` | 事实记录（做到哪一步），不承担规格职责 |

> 一句话：**规格看代码，进度看状态文件，经验看记忆**。这次发现的冲突，绝大多数是"文档没跟上代码"。

## 三、真冲突（4 处，已修）

### A1 `workflow.py` S10 印着一条不存在的命令 `--sync-from`

- **冲突**：S10 的标准命令是 `subtitle.py ... --stage ass --sync-from asr（若可用）`，
  但 `subtitle.py` 的 argparse **没有 `--sync-from`**（只有 `--stage align|cues|ass|master|upscale|render|all`）。
  照"机器真源"敲命令 → `error: unrecognized arguments`。
- **由来**：`docs/patches/2026-10-21_实跑优化建议修复记录.md` 的 10.4 条当时只写了**建议**，
  有人把建议当成了已实现，抄进了 `workflow.py`。
- **修法**：S10 命令改为真存在的 `--stage align`（真对齐：CTC + whisper 校时），
  补丁记录 10.4 从「⏸ 未修」改为「✅ 已落地（换了做法）」，并写明原参数从未实现。

### A2 `bgm check` 与 `bgm mix` 读的不是同一份增益

- **冲突**（实测 ep29）：盘上的计划写 `gain_db=-3`；`bgm check` 直接读盘 → `[FAIL] B009 最终铺底 -20.4 LUFS 过高`；
  而 `bgm mix` 里先跑 `sync_plan_gain()` 按库里实测响度校正成 **-14.6** 再混 → `[OK]`。
  同一集，一个说不能混、一个混成功了。
- **为什么会有**：`sync_plan_gain()` 只在 `mix_episode()` 里调用，`cmd_check()` 没调。
  （V0.7.5 修了 `plan` 侧的同类问题，漏了 `check` 侧 —— 30 集旧计划全是这个状态。）
- **修法**：`cmd_check` 先做同样的校正（**只改内存不写盘**，并打印"本次判定按校正后的值"），
  再判门禁。新增用例 `test_76_check_and_mix_read_the_same_gain` 钉住"两边必须是同一个 dB 值"。

### A3 S6 判据「分段成片 ≥ 镜头数」实际按**文件数**算

- **冲突**（实测）：本项目 240 个镜头，`workflow status` 报 **284/240** 达标。
  因为返工时新批次没删旧批次，同一镜在多个 `chain_epNN/` 下各有一份 `final.mp4`，
  判据把重复文件都算了 —— **缺 20 个镜头也看不出来**。
- **修法**：probe 支持 `"count": "parent"`（按父目录名去重后再比阈值），S6 启用。
  现在报 **240/240**，数字与实际镜头一一对应。新增用例 `test_26b`。

### A4 总纲把封面主路径写成 `cover_forge.py`

- **冲突**：`生产流程总纲.md` 环节 14 的载体写 `cover_forge.py`（PIL 叠字），
  而 `发行资料清单.md`、`README`、`workflow.py` S7 全部是 **`cover_prompt.py`（AI 直出带字）为主路径、
  `cover_forge.py` 仅兜底**。照总纲做就会走已被否决的路线。
- **修法**：总纲改为 `cover_prompt.py`（主路径；`cover_forge.py` 仅兜底）；
  `技能映射与缺口.md` G5 补一句「2026-10-20 起主路径改为 AI 直出带字」。

## 五、命名撞车（1 处，保留并标注）

`docs/orchestration/技能映射与缺口.md` 用 **G1–G10** 编「能力缺口台账」（G5=发行资料、G10=画风三轨），
而 `生产流程总纲.md` 用 **G-0…G11** 编「门禁」（G10=流程顺序门禁）。

- **为什么不改**：两套编号已出现在历史补丁记录与版本号引用里，改名会制造更多悬空引用。

  在 `技能映射与缺口.md` 里是缺口编号，在 `总纲 §四` 里是门禁编号。本节即为该标注。

## 九、歧义专项（V0.7.8，2026-10-22 追加）

> 用户追加要求：「放大的环节改成 1080P，不要设置 2k 了；检查一下全部内容，
> 看有没有会让项目产生歧义的地方」。§三 查的是**互相打架**，本节查**说法不唯一** ——
> 不打架、能跑通，但同一件事有两种理解，人或 Agent 会照错的那个做。

### 9.1 已修：命名在说谎（最严重）

**`<ep>_master_2k.mp4` 实际是 1080×1920。** 竖屏项目的 `config.upscale.json` 写的是
`target = {mode: exact, width: 1080, height: 1920}`，产物却叫 `_master_2k` ——
而「2K」通常指 2560×1440。后果：隔一周看目录会以为"已经出过 2K 版"，
用户本人就是照这个名字提出「不要 2K，要 1080P」。

**修法：正名，不迁移老项目。**

| 项 | 旧 | 新 |
|---|---|---|
| 产物的名字 | `<ep>_master_2k.mp4` | `<ep>_master_<W>x<H>.mp4`（竖屏 → `ep03_master_1080x1920.mp4`） |
| 读取 | 只认旧名 | **新名优先，旧名回退**（`upscaled_path()` / `bgm._hi_res_names()` / `release_export` 的 `master_res` 档） |
| 在跑项目 | — | 30 集已改名（`_master_2k` → `_master_1080x1920`），改名后 `workflow status` S9 仍 30/30 |

涉及：`upscale.py`（产出）、`subtitle.py`（读写/停点提示）、`bgm.py`（底片与时长的候选名）、
`release_export.py`（来源优先级，带分辨率的排在 `_master_2k` 之前）、`workflow.py`（S9 判据）、
项目侧 `tools/asr_burn.py`。

**为什么不是"直接把 target 改成 2K"**：用户要的是 1080P，且 1080P 是平台下限的交付规格
（`resolution.deliver = 1080x1920`）。问题从来不在分辨率，而在**名字和分辨率不一致**。

### 9.2 已修：`--ep` 有两种写法，错的那种不报错

`--ep 26` 能通过参数校验，`_belongs_to_ep()` 也能匹配到 `ep26_sc02` 的分镜，
但 `align/cues` 的路径被拼成 `subs/26/` ⇒ **静默产出 0 条字幕**，还顺手建了个空目录。
（实测：`② 字幕条目：0 条 ｜ 覆盖 0.0s`，退出码仍是 0。）

修法：`subtitle.py` / `upscale.py` / `bgm.py` 三处入口统一 `canon_ep()`
（`26` / `ep26` / `EP26` / `ep026` → `ep26`；非数字直接报错退出码 1），并清掉误建的 `subs/26/`。
新增 3 例测试钉住。

### 9.3 已修：两份「高清放大」文档，且都指向不存在的文件

- `stages/subtitle/references/hd-upscale.md` 指向 `<workspace>/docs/高清放大-2K-实测与操作手册-2026-09-21.md`
- `upscale.py` 的报错提示也指向 `docs/高清放大-2K-实测与操作手册.md`
- 而在跑项目的 `docs/` 里**根本没有这两个文件**；真正的 245 行手册在
  `stages/production/references/hd-upscale-2k.md`

修法：手册改名 `hd-upscale-case-2560x1480.md`（标题与首段注明"2k 是历史叫法，指本案例的目标分辨率"），
两处引用改成**仓库内相对路径**，不再指向工作区。

### 9.4 已写明：术语一词多义（保留，但给出唯一解释）

| 说法 | 有几种意思 | 唯一解释 |
|---|---|---|
| **母版** | 4 种 | ①`<ep>_master.mp4`=拼接母版（无字幕）；②`<ep>_master_<W>x<H>.mp4`=放大母版（无字幕，字幕烧在它上面）；③`<ep>_mix.mp4`=混过 BGM 的底片；④`<ep>_subbed.mp4`=成片。**发布版只有 `09-发行/剧集/EpisodeNN.mp4`**，其余都叫中间产物 |
| **2K** | 3 种 | 曾同时指「产物名」（其实 1080P）、「那台横屏案例的 2560×1480」、「平台意义的 2160×3840」。**今后一律写具体 `宽x高`，不用 k 简称** |
| **字/秒（cps）** | 2 种 | 中文按**汉字**计，西语按**字符**计（不是单词）；`spoken_len()` 已剔标点 |
| **续跑** | 2 种 | `video run --resume <批次>`=同环节内不重复扣费；`pipeline run --from S<N>`=跨环节继续 |
| **"没过"的退出码** | 3 种 | **4**=环境/前置/顺序/待内容（补齐再跑）；**2**=产物门禁不合格（改产物）；**3**=预算熔断（加钱或缩范围）。不要混用 |
| **G + 数字** | 2 套 | `G-0/G-1`=前置门禁；`技能映射与缺口.md` 的 `G1–G10`=能力缺口编号；`总纲 §四` 的 `G10/G11`=门禁编号 |
| **voice** | 2 处同义 | 真源是 `project-setup.json` 的 `video_options.voice`（声音归属）；`h3_prompts[*].voice` 是 `convert_storyboard` 抄过去的**副本**，改副本无效 |

### 9.5 建议统一（未改，需拍板）

1. **集号写法**：命令统一 `epNN`（两位）；发布版统一 `EpisodeNN.mp4`；目录名不要出现 `ep1` / `EP01` / `第3集`。
   现在靠 `canon_ep()` 兜，但**目录与清单里已有的历史写法**没统一。
2. **镜头 vs 段**：「镜」= 剧本里的 `[SC-nn]`（一个叙事单位）；「段」= 一个 `final.mp4`（一个视频文件）。
   两者一一对应，但文档里混用（"分段成片"/"镜头数"/"8 段"/"240 镜"）。建议：正文一律写「镜」，
   只有涉及视频文件时写「段」。
3. **分辨率写法**：`1080P` / `1080x1920` / `hd` 三种写法并存，建议对外一律 `宽x高`，`1080P` 只在口语里用。
