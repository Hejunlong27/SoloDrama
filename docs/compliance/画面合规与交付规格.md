# 画面合规与交付规格（平台驳回三类问题的根因与根治）

> 2026-10-30 新增。配套代码：`delivery_spec.py` / `compliance_media_check.py` /
> `release_export.py`（出口门禁）/ `subtitle.py`（渲染内归一化）/ `prompt_templates.py`（品牌负向）。

平台驳回文案看起来是三个独立问题，实际是**三条不同的链路缺口**。逐条给根因、证据、修法。

---

## 一、检测到视频画面中存在黑边（最高频）

### 1.1 结论先行

**画面里没有黑边。** 本地 `cropdetect` 对 1466 帧全量检测全部返回 `crop=1080:1920:0:0`（满幅）。
真正的成因是**交付规格的显示比例不是 9:16**，平台按显示比例重新适配播放器时补出了边。

### 1.2 数据链（实测，2026-10-29 项目 `D:/剧本/海外剧/4`）

| 环节 | 尺寸 | SAR | 显示比例（DAR） | 与 9:16 的偏差 |
|---|---|---|---|---|
| H3 出片 | 672×1216 | 1:1 | 21:38 = **0.5526** | −1.75% |
| 整集母版 | 672×1216 | 1:1 | 0.5526 | −1.75% |
| RH_Astra 放大（按源比例吸附） | 1062×1920 | 1:1 | **0.5531** | −1.67% |
| 交付层（`scale=1080:1920` 硬凑） | 1080×1920 | **59:60** | 0.5531 | −1.67% |
| 平台 9:16 播放器 | 1080×1920 | 1:1 | **9:16 = 0.5625** | 0 |

平台把 DAR 177:320 的内容塞进 9:16 容器，只能补边：

* 按高适配 ⇒ **左右各 9px**（`(1080 − 1062) / 2`）
* 按宽适配 ⇒ **上下各 16px**（`1080 × 320/177 = 1952.5`，`(1952.5 − 1920)/2`）

### 1.3 为什么本地自查永远查不出来

`1080×1920 + SAR=59:60` 是「**用非方形像素骗过容器**」：容器元数据看着是 1080×1920 完全合规，
实际显示比例是 0.5531。`cropdetect` 扫的是**像素**，像素被拉伸过，四边全是画面内容 ⇒ 满幅。

这和「画面里真的有一圈黑」是两回事。只要判据还停留在「有没有黑像素」，这个缺陷就永远漏检。

### 1.4 生成端为什么给不出 9:16

`megapixels=0.8` + `ratio=9:16` 交给平台，平台按 **32 像素对齐** 取整：

```
9:16 且面积 0.8MP  ⇒  W ≈ 670.8, H ≈ 1192.5
对齐 32            ⇒  672 × 1216   （0.817MP，比例 0.5526）
```

精确 9:16 且 32 对齐的最小组合是 **720×1280**（0.92MP，成本 +15%），没有 0.8MP 的解。
⇒ **不要指望调 `megapixels` 修好它**，归一化层是唯一可靠解。

### 1.5 根治：crop-to-fill（绝不 pad）

```
scale=trunc(iw*sar/2)*2:ih,                                ← ① 先按 SAR 还原真实显示宽度
setsar=1,
scale=1080:1920:force_original_aspect_ratio=increase,      ← ② 放大到刚好覆盖
crop=1080:1920,                                            ← ③ 中心裁切（默认居中）
setsar=1
```

三步顺序不能换：

1. **先还原**：`iw*sar` 把 SAR 59:60 的文件还原成 1062 宽，否则后面的 scale 会接着沿用那 1.69% 的拉伸，
   改了个寂寞。
2. **`increase` 不是 `decrease`**：`decrease` 会留余量，留了余量就只能 pad，pad 就是制造黑边。
3. **裁掉的是 1.69% 的边缘**：672×1216 → 1080×1954 → 裁到 1080×1920（上下各 17px）。
   构图略紧完全可以接受，比被平台驳回便宜得多。

代码：`delivery_spec.build_normalize_vf()` / `subtitle.norm_filter()`（同一套逻辑，两处各带一份，
因为 `subtitle.py` 可能被单独拷进 Skill 包运行）。

### 1.6 落地位置（零额外成本）

归一化**挂在烧字幕那一步**，不新增工序：

```
母版 672×1216
  → ensure_delivery_spec()   ← 归一化到 1080×1920 / SAR 1:1（重编码一次）
  → write_ass(canvas=1080×1920)
  → stage_render()            ← 在已归一化的底片上烧字幕（第二次重编码，不可避免）
```

顺序不能反：ASS 的 `PlayRes` 一旦按放大母版的 2560×4632 写好，烧到 1080×1920 上虽然 libass 会
按比例缩放，但 `qa_safe_area` 的断言口径就和实际画面不一致了。

`--no-normalize` 可关闭（仅供排查），**默认开启**。

### 1.7 出口设卡（最后一道）

`release_export.py` 默认对每个候选源做规格判定，不合格**不进导出计划**：

```
[FAIL] 第 1 集源不合规（ep01_master.mp4）：显示比例 0.5526（672×1216）≠ 0.5625，
       偏差 1.75% ⇒ 平台适配 9:16 播放器时必然补黑边；像素格式 yuv420p10le ≠ yuv420p；
       不是烧过字幕的成片（文件名无 `_subbed`）
[BLOCK] 发布版导出未完成 —— 共 3 项问题（退出码 2）
```

临时预览可加 `--no-media-check`。横屏项目用 `--target 1920x1080`。

## 二、检测到视频画面中出现品牌 logo

### 2.1 根因

两处缺口叠加：

1. **提示词层**：`prompt_templates.BAN` 只禁了「文字/字母/数字」，管不住**图形商标**
   （勾、咬了一口的苹果、三叶草、四环）和**去字化的配色标识**（红底白字方块、双 C 扣）。
2. **出片层**：没有任何抽检，靠模型自觉。

### 2.2 前置规避（已改）

`stages/assets/scripts/prompt_templates.py` 的 `BAN` 增加：

> 禁止出现任何品牌标识与商标：含服装鞋包、手表首饰、手机电脑、汽车车标、店招门头、
> 商品包装上的可辨识 logo、图形化商标（勾/条纹/齿纹/字母组合徽标）、
> 以及靠特定配色与版式即可认出品牌的标识性设计；上述物件一律用无标识的通用款；

一处改动，角色/场景/道具三类资产图全部生效（`BAN` 是三类共用）。

### 2.3 出片抽检（`C4`）

**不做伪自动检测**：本机无 vision provider，任何"疑似 logo 已通过"的结论都是假的。
只做确定性的事——抽 12 帧拼成 4×3 一张图，人看一遍（3 秒扫完整集）：

```
08-合规/抽帧/Episode01_抽帧.jpg
```

重点查：角色服装 logo、手机/手表品牌、店招与包装上的可读商标。

### 2.4 附带风险（本轮抽帧发现）

画面里出现**大面积可读文字道具**（手写信件、报纸、书页特写）同样可能触发
「未授权文字/水印」类驳回。这不是品牌 logo，但审核口径相邻。

建议：道具提示词里避免"满屏可读文字"，需要信件时用「笔迹模糊/侧逆光/局部特写」。

## 三、检测到视频画面中不包含字幕

### 3.1 根因：流程停点 + 出口无校验

`subtitle.py --stage all` 开高清放大时，**设计上就停在「无字幕放大母版」**，把决定权交回用户：

```
 %dx%d 母版已就绪（无字幕）：<ep>_master_1080x1920.mp4
 要不要加字幕？（这一步要你确认，因为烧字幕要重编码一遍，约 1–3 分钟）
   要 → subtitle.py --ep ep01 --stage render
   不要 → 直接交付上面那个 mp4
```

这个停点是用户明确要求的，**保留**。问题出在下一环：
`release_export.py` 只看文件名 rank 和 mtime，不校验内容，于是**无字幕母版一路绿灯进发行目录**。

实测 `D:/剧本/海外剧/4`：`report.json` 里 `align_methods` 全部 `missing`、`cues` 字段缺失、
`subs/ep01/` 下没有 `.ass`、没有 `_subbed.mp4` —— 全 3 集都是母版直接发的。

### 3.2 三级证据链（`C3`）

| 级 | 判据 | 说明 |
|---|---|---|
| ① 产物名 | 必须含 `_subbed` / `_hardsub` / `_hard_sub` | 母版、放大版、归一化中间件一律不是可发布形态 |
| ② 渲染报告 | `report.json` 的 `cues > 0` 且 `verify_render.pass is True` | 直接读 `subtitle.py` 自己的渲染自检结论，不重复造 |
| ③ 像素启发式 | 字幕带（画面 50%–70% 高）抽样帧中 ≥25% 出现近白像素（Y ≥ 210） | 兜底，没有报告时才依赖它 |

任一级不成立即 `FAIL`。判据刻意「宁可误杀」——放行一集就白跑一次审核周期。

### 3.3 为什么字幕检测看 60% 高度

`config.subtitle.json` 的 `placement.anchor_top = 0.6`（视觉中心 6:4，移植自 vidpure），
字幕块中心落在画面 60% 高处，不是常见的贴底。C3 的字幕带按 `0.6 ± 0.1` 取样。

## 四、日常用法

```bash
# ① 出片（字幕 + 归一化一次完成；默认就归一化）
python stages/subtitle/scripts/subtitle.py --workspace "<ws>" --ep ep01 --stage render

# ② 画面侧门禁（C1 规格 / C2 黑边 / C3 字幕 / C4 品牌抽帧）
python stages/production/scripts/compliance_media_check.py --workspace "<ws>" --ep ep01 --sheet
python stages/production/scripts/compliance_media_check.py --workspace "<ws>" --all --json

# ③ 导出（默认过门禁，不合格退出码 2）
python stages/production/scripts/release_export.py --workspace "<ws>" --all --apply

# 单文件体检 / 手工修
python stages/production/scripts/delivery_spec.py check "Episode01.mp4" --edges
python stages/production/scripts/delivery_spec.py normalize "in.mp4" -o "out.mp4"
```

## 五、验收口径

| 项 | 通过条件 | 机器可判 |
|---|---|---|
| C1 交付规格 | 1080×1920 / **SAR 1:1** / 显示比例 0.5625±0.3% / yuv420p | ✅ |
| C2 内容层黑边 | 四边均无「纯色暗边」（YAVG ≤ 20 且动态范围 ≤ 14，跨帧一致） | ✅ |
| C3 硬字幕 | 产物名 `_subbed` + `verify_render.pass` + 字幕带白字 ≥25% | ✅ |
| C4 品牌 logo | 12 帧拼图人看一遍，无可辨识商标 | ❌ 人工 |

## 六、别忘了

* **不要 pad**。任何「补一圈边把比例凑齐」的写法都是在给平台递驳回理由。
* **不要用 SAR 凑容器**。容器元数据对、显示比例错，本地全绿、平台全红。
* **归一化中间件不是发布版**。命名 `_normdelivery` 且 `release_export._rank()` 强制排最后，
  防止它抢在 `_subbed` 前面被导出。
